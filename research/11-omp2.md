# 11 — omp²: from a chat loop to an owned systems architecture
> Slice 11 · Researched 2026-10-08 · Scope: the complete September playbook, official pre-release branch and architecture records, release/migration evidence, measurements, and a full ~3-minute chapter; source/document inspection only, no build or runtime validation.

## Narration-ready takeaways

- **omp² is real public pre-release work, not just a teaser and not the installed 18.8.6 release.** The official `omp2` branch calls itself a Rust rewrite and warns of breaking changes; the product homepage still says “omp², soon!”, while GitHub labels v18.8.6 the latest release. [2][3][8]
- **The motivating criticism includes omp itself.** Bölük says message history, extension state, background jobs, configuration, and UI/controller state accumulated separate owners; the replacement tries to make the engine own that complexity instead of every extension reimplementing recovery. [1][4]
- The playbook's exact five consequences are **“One authoritative session,” “A trusted control plane,” “Bounded work,” “Explicit compatibility,” and “Views are projections.”** They are design commitments, not five independently shipped product announcements. [1]
- **The journal is meant to reconstruct the session, not merely record the conversation.** The essay's materialized tree includes messages, tools, jobs, todo state and queues, so rewind, fork, resume, prompts and views derive from the same authority. [1]
- **Keep policy outside the execution boundary.** The trusted host owns session state, routing, approvals and limits; the intended sandbox contains an obedient execution stub. The implementation record explicitly calls the minimized remote/container/VM stub incomplete. [1][32]
- **Settings and loop ownership become engine concepts.** Convars declare scope and persistence; the essay calls the composable across-turn behavior primitive a Director. Its documented example nests Plan and ForceTool rather than making modes coordinate through private flags. [1]
- **“Compatibility” first means model/provider semantics, not a promise that old plugins work unchanged.** A compiled rulebook owns quirks and precedence; the concrete KDL refactor cited by the essay is already present in shipped omp v1 history. [1][9][10]
- **The UI is a view, not another state owner.** Typed components and a single rendering pipeline are intended to support terminal, remote and inspector views; the formal appendix concerns a particular transcript protocol, not a proof that the whole application is bug-free. [1][15]
- **The strongest evidence is architectural, not an omp² coding leaderboard.** The creator reports renderer and tool-roster measurements, and the technical report reports bounded TLA+ model checks; their scopes and caveats must stay attached. [1][15]
- **Migration machinery exists, but a full upgrade guarantee does not follow.** The official branch has legacy configuration conversion and storage relocation; its opened transcript importer names Claude Code and Codex, not old omp sessions. [65][66][67]
- **There is no dated public release commitment in the opened roadmap evidence.** The August 26 “no public release date or ETA” answer is from the project's automation account, not a quotation from Can Bölük; the September essay still describes work ranging from shipped to being thought through. [1][11]

### 2. Why the current architecture motivates a replacement

| Problem in the author's account | Concrete consequence | Proposed owner |
|---|---|---|
| The message tree is journaled, but counters, todo state, retry state, tool roster and extension closures can live elsewhere. | Rewinding a conversation need not rewind the rest of the session; resuming can restore different state. The essay supplies nine version-pinned Pi extension examples, while explicitly including omp in the criticism. | One journal-derived authoritative session and engine-owned fold. [1] (“The state,” Appendix A) |
| One tool call is split into `renderCall`, `execute`, and `renderResult`. | Preview and execution can reopen/recompute the same edit; renderers parse a model-facing string to recover structure already available during execution. | One typed streaming call lifecycle with structured input, result, diagnostics and usage. [1] (“The runtime”) |
| Truncation and backgrounding are opt-in per tool. | Uneven size limits, compounded truncation inside Eval, duplicate spawn/poll/message/kill APIs, and calls that hold the conversation indefinitely. | Central output/blocking limits, artifacts, and a single job primitive. [1] (“Limits are part of the primitive”) |
| Cancellation is merely cooperative when extension code shares the engine's isolate. | A forgotten signal or synchronous loop can keep work alive after a timeout. | A resource-owning process/worker boundary the host can terminate. [1] (“Cancellation requires a kill boundary”) |
| Settings flow through a large session object; modes depend on separate flags/private mutexes. | Persistence, inheritance and mutually interacting loop behaviors require caller-specific plumbing. | Convars for values; Directors for across-turn behaviors. [1] (“The control plane”) |
| Model/provider differences are repeated as name checks across builders. | Adding one quirk requires several coordinated branches; “unsupported” can be confused with “unknown.” | Taxonomy, lineage/class rules and provider overlays with checked precedence. [1] (“The inference”) |
| An ANSI-escaped `string[]` conflates layout, style, content and transport. | Repeated parsing/measurement/allocation; extensions must also remember width handling, sanitization and theme conventions. | Typed components and one final rendering/materialization boundary. [1] (“The interface”) |

These are **the creator's dated diagnosis**, not an independent October 2026 audit proving that Pi or any competitor still has every cited defect. Appendix A links a specific Pi source revision, `853a80d26c90a14c1886f0ebb8ffaae133ca2185`; do not animate its failures as a current comparison without separately checking current code. [1]

### 3. The design envelope and the five exact architectural consequences

The four operating modes are **Multiplexed workspace** (many local agents sharing a workspace), **Remote driver** (a client controlling a remote/cloud agent), **Spectator** (an observational web client), and **Factorio** (an autonomous software factory against hostile inputs). “Factorio” is the essay's architecture-test nickname, not an announced game integration or separate shipped product. The author argues that designing for all four prevents local-TUI assumptions from silently becoming system-wide constraints. [1] (“The design envelope”)

1. **One authoritative session.** The essay chooses an XML/DOM-shaped materialization but explicitly allows an ECS or other representation if the invariant holds. The live tree is the session representation; the journal stores incremental changes from which it is reconstructed. Caches may accelerate access but must not become another truth. A `<subagent>` disappearing during a rewind provides lifecycle work; prompts query the same state. This is session-state rewind—not a demonstrated ability to reverse arbitrary network or filesystem side effects. [1] (“The state”)[17] (“External Updates”)
2. **A trusted control plane.** Session storage, inference, policy, routing, approvals, limits and journaling stay with the host. An untrusted execution environment receives bounded requests and returns bounded results. The branch's process documentation describes the concrete `omp-env` client / trusted `omp-envd` host split, supervised Python hosts and workers, and framed IPC. The ADR says the remote/container/VM side still uses the full envd binary instead of the separately minimized stub. [1] (“The runtime”)[24][32]
3. **Bounded work.** Tool calls are cancellable streams rather than opaque functions returning strings. The essay unifies ordinary calls, subagents, shells, remote functions and daemons as jobs with streams, status and signals; output truncation belongs in the conversation projection while full data can remain available as artifacts. “Bounded” is a property to enforce at actual boundaries, not a blanket claim that every queue in the implementation has a finite bound: the actual Kernel constructor uses `flume::unbounded()` for its command mailbox. [1] (“The runtime”)[64]
4. **Explicit compatibility.** The essay names `taxonomy/` (“what model is this string?”), `classes/` (“what is true of this model lineage?”), and `providers/` (“what does this host change?”). Unknown directives or values and equally specific conflicting rules are errors; no matching rule is unknown, not false. Higher layers express semantic intent—such as requiring a tool call—while inference chooses soft prompting, a free native constraint, bounded escalation or an explicit failure. Grammar budgets, dialect normalization, malformed-output repair and capability receipts belong here too. [1] (“The inference”)
5. **Views are projections.** The controller owns session state; TUI, remote client and subagent inspector consume snapshots/changes and send actions back rather than directly mutating that authority. A typed tool element can have distinct model, human, journal and inspector projections without reparsing a formatted result string. The component/renderer contract is therefore connected to the state contract, not merely a visual redesign. [1] (“Controller and actor,” “The interface”)[5]

**Important naming distinction:** the session DOM models authoritative session facts; the UI component tree models presentation. “DOM” here does not require a browser or Electron. The stack choice in the essay is a Rust engine and embedded Python extensions. [1] (“The state,” “A typed component model,” “The stack”)

### 10. Narration draft for a full ~3-minute chapter

*Editorial draft, approximately 400 words; timing is a production target, not measured speech duration. Citations are evidence-card cues, not spoken text.*

> There is a second omp taking shape. It is called omp squared: a public Rust rewrite, explicitly marked pre-release. It is not the same thing as the omp 18.8.6 we have been demonstrating. [2][3][8]
>
> Its creator, Can Bölük, frames the rewrite around one sentence: “Unavoidable complexity needs an owner.” This is not just criticism of other tools. His playbook describes what omp itself got wrong. Saving the messages was not always enough to save the session: the task list, active tools, background jobs and extension state could live somewhere else. Rewind the conversation, and those other pieces might disagree about where you are. [1]
>
> The proposed answer is one authoritative session, reconstructed from its journal. Imagine a tree containing the conversation, tools, queues and jobs together. Rewind, resume, a remote client and an inspector should all derive their answer from that same state—not maintain separate versions of the truth. XML is a convenient representation here, not the magic ingredient. [1]
>
> The next boundary is trust. The host keeps session ownership, policy, routing and limits. Execution happens across a boundary the host can control. Tools become bounded, cancellable streams, while long-running calls and subagents share a job model. Stopping work should mean stopping the work, not merely stopping the wait. The minimized remote execution stub is still explicitly partial. [1][32]
>
> Configuration and workflow also get owners. Convars attach persistence and scope to each setting. Directors compose behavior across turns: a plan can require a tool, then hand control back to its parent. Meanwhile, a separate compatibility rulebook decides how a particular model and provider can satisfy that request. Part of that rulebook architecture has already shipped in the existing omp line. [1][9][10]
>
> Finally, the interface becomes a projection. Terminal, native and inspector views consume state rather than becoming additional controllers. Typed components replace repeated string manipulation. There is even a formal model for how concurrent live blocks become ordered terminal history—but that is a claim about a specific protocol, not a proof that the whole application cannot have bugs. [1][15][31]
>
> So this is more than a wish list, and less than a finished product. The public records identify implemented components alongside explicit gaps: grammar budgets, complete web projection, remote placement, and an embedded tiny model. You can inspect the source today. What we cannot promise is a stable migration or a launch date. The interesting idea is the engineering contract: put shared complexity somewhere that owns it. [3][11][47][49][57][62]

## Contested or uncertain

- **Some official architecture prose describes a different target than the code.** `agent-loop.md` presents Agent/Arbiter/Regime APIs, while the actual public source exports Directors and reconstructs `DirectorStack` from the Session DOM inside `Kernel<C>`. The source resolves the chapter vocabulary in favor of Kernel/Session/Directors; the conflicting prose is not evidence that Directors were superseded. Other path/API claims in those design documents require the same caution. [23][63][64]
- **Confinement status is internally inconsistent.** The Python overview retains an August 19 “no sandbox enforcement” ruling, yet the current sandbox README describes Seatbelt, Bubblewrap, Landlock/seccomp, gVisor, Docker/runsc and AppContainer plans. Neither proves the effective default confinement of a live extension host. Do not narrate killable workers as a proven security sandbox or the old ruling as a complete description of all current backend code. [68][69]
- **An accepted decision is not a finished system.** ADR 0006 marks the minimized sandbox stub partial; ADR 0023 says there is no embedded tiny local model for harness chores. The homepage's “soon” and the branch's pre-release warning overrule any attempt to market the whole record set as a shipped release. [2][3][32][49]
- **Formal verification has a scope.** The PDF presents hand proofs and reports finite TLC runs against `ElasticSlots.tla`; this is not independent peer review, a proof of the Rust implementation's refinement, or a guarantee that every terminal/emulator is bug-free. ADR 0034 also contains a “Viewport geometry (cutover plan)” with a different presentation policy, reinforcing the need to name the exact model rather than say “the TUI is mathematically perfect.” [15][60]
- **Numerical inconsistencies remain unresolved.** The extension-example count misses one example; the renderer's HTML metric strip and prose disagree on `.includes` CPU share. The tool-roster figure varies turn counts and batching as well as schemas, and does not document task success or the complete inference setup. Do not derive a universal omp² speedup from any of these. [1]
- **Build-readiness reports are not release notes.** PR #12121 remains an outsider's report of clean-checkout compile/test-target problems, with an offered fix; it is useful evidence of pre-release rough edges, not a reproduced result from this investigation or an official assurance that every build fails. [14]
- **No independent omp² coding-quality evaluation was established in the opened sources.** The renderer profile, tool-roster sweep, and formal transcript model measure different things; none is an omp² SWE-bench/Terminal-Bench accuracy score. [1][15]
- **The author’s language preferences are opinions/design experience, not established comparative research.** Rust and Python choices are first-party architecture decisions; claims about what agents “write better” should be attributed rather than generalized across models and projects. [1][4]

## Corrections & nuances to the blueprint

1. Upgrade the previous “documented but partly in progress” teaser to a full chapter with the public branch and implementation-status register—but retain a persistent **pre-release / design** badge. Public source is more than a proposal; it is not a stable release. [2][3][26]
2. Do not label the shipped v18.x release line “omp².” The latest release is v18.8.6; the rewrite is the separate `omp2` branch. Likewise, the essay's KDL refactor is concretely in v18.x history and should not be advertised as something users must wait for omp² to obtain. [3][8][9][10]
3. Teach **ownership**, not “XML is magic” or “Rust fixes agents.” XML is a chosen inspectable representation, with alternatives expressly allowed; the invariant is journal-derived authority. [1]
4. Use the exact five consequence names. “Bounded execution” is a sensible paraphrase, but the essay's heading-level term is **Bounded work**; “multiple UIs” is an outcome of **Views are projections**. [1]
5. Keep provider compatibility, revisioned tool-history compatibility and user migration as separate topics. They have different mechanisms and evidence. [1][4]
6. Keep Tern separate. Its official page says **closed beta** and presents it as a terminal/workspace built for omp. Its Surface Protocol is a semantic component protocol with ANSI fallback; neither the existence of Tern nor its omp demos proves that omp² has launched. Shipped v18.8.6 itself includes Tern/TSP fixes. [8][19][20]
7. Current terminal recreations should remain **omp 18.8.6**, exactly as requested. Explain omp² with architecture animation or explicitly source-labelled pre-release material; do not pass off the essay's mockup or schematic as a capture of installed defaults. [1][3][8]
